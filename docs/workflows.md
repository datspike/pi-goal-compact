# Рабочий процесс

## Публичное и локальное

| Слой | Что в нём лежит |
|---|---|
| Git | Код, тесты, `README.md`, решения в `docs/adr/` и переносимые правила |
| `.task_files/` | Приватные планы, вопросы, решения владельца и передачи работы |
| `.runtime/` | Локальные результаты проверок и модельных прогонов, снимки и журналы |
| `AGENTS.local.md`, `.pi/` | Правила этой машины, настройки и состояние инструментов |

`.gitignore` защищает локальные слои, список `files` в `package.json` ограничивает состав пакета, а `npm run check:public` проверяет и то и другое. Внешнему участнику приватный слой не нужен: всё необходимое для вклада лежит в Git.

## Перед новой работой

Прочитайте `AGENTS.md` и, если он есть, `AGENTS.local.md`. Личная инициатива начинается с `.task_files/INDEX.md`: в нём задачи и их зависимости, а не перечень журналов. Карточка задачи называет результат, статус, зависимости, следующий шаг и критерий завершения. Изменили карточку — в той же работе обновите индекс.

| Статус | Что разрешено |
|---|---|
| `ready` | Выполнение в утверждённых границах |
| `planning` | Сбор фактов и подготовка решения без изменения кода расширения |
| `awaiting_decision` | Ожидание конкретного решения владельца |
| `deferred` | Только планирование; не реализация и не модельный прогон |
| `claimed` | Работа закреплена за названной сессией и worktree |
| `done`, `reference` | Проверенный итог либо материал для зависимой работы |

Отложенная идея — не утверждённая задача.

## Решение до кода

Большая или неясная работа сначала получает краткий бриф: чего хочет владелец, что не входит, чем это будет доказано. Нерешённые варианты живут в приватной карточке. Принятое решение, которое меняет договор или устройство расширения, переносится в `docs/adr/` до реализации.

## Проверка изменения

1. Найдите ближайшую реализацию, её вызывающие места и тесты.
2. Воспроизведите затронутое поведение адресным тестом.
3. Измените код и запустите `npm run verify`.
4. Поведение, видимое владельцу, проверьте на пользовательском пути: в настоящем TUI с отдельным каталогом настроек Pi, без запросов к модели.
5. Перед коммитом выполните `git diff --check` и посмотрите состав коммита.

Если правка задевает автомат цели и сжатия, сверьте её с моделями в `formal/`: навык проверки лежит рядом с ними.

Модельные прогоны — отдельный шаг с согласованным бюджетом. Их итог не сводится к баллу оценщика: по каждому случаю отдельно сказано, сделана ли задача.

## Коммиты и публикация

Один коммит — одно связное изменение в формате Conventional Commits. Подготовка плана сама по себе не разрешает ни коммит чужих изменений, ни push, ни запрос на слияние, ни публикацию пакета.
