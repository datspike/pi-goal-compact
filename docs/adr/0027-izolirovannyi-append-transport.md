# 0027. Изолированный способ отправки запроса сводки

## Контекст

Обычная сводка сериализует назначенные сообщения в отдельный запрос. Append должен продолжить уже отправленный рабочий префикс, не меняя сохранение сжатия и продолжение цели. Обработчик `session_before_compact` выполняется раньше подготовки следующего рабочего запроса, поэтому внутри него нет готового следующего запроса, который можно просто заменить.

## Решение

В экспериментальной версии отделить подготовку входа и отправку сводки от существующих проверок ответа. Необязательный внутренний способ отправки получает назначенные сообщения и те же инструкции обычной сводки. Он обязан оценить весь вход, вызвать проверки окончательного запроса перед сетью и вернуть обычный ответ провайдера. Валидация ответа, отмена, принадлежность операции, файловые наводки и фиксация остаются у прежних владельцев.

Append использует окончательный запрос, захваченный после всех обработчиков отправки. После него допускается только добавление сообщений, не замена прежнего префикса. Объявления инструментов сохраняются, но вызов запрещён вне модели и проверяется по ответу. При разрезанном ходе история и ранняя часть обрабатываются существующими отдельными вызовами: новый специальный разделитель в ответ модели не вводится.

Захват охватывает оба метода провайдера, `stream` и `streamSimple`: SDK может выбрать любой из них для рабочего запроса. Продолжение использует тот же метод. После всех обработчиков Responses проверяется не только исходный префикс, но и фактический `max_output_tokens`: положительное целое, не больше разрешённого максимума сводчика.

Эксперимент включается только явно; обычная рабочая установка и настройки не меняются.

## Альтернативы

- Перенести старое расширение целиком: оно дублирует уже существующее управление сжатием, отменой и продолжением.
- Запустить служебный пользовательский ход внутри ожидающего compact: он меняет журнал и жизненный цикл, допускает инструменты и создаёт зависимость вложенного хода от завершения сжатия.
- Пересобрать последний запрос из JSONL: журнал не содержит окончательных преобразований запроса.
- Переписать ядро Pi для нового подготовительного API: не требуется для ограниченного эксперимента.

## Последствия

Один необязательный способ отправки добавляется только в генерацию сводки. Обычный путь без него остаётся прежним. Технические проверки отправки не объявляются доказательством смысловой сохранности. Сопоставление источников с захваченным контекстом должно быть однозначным; неизвестное преобразование ведёт к явному отказу до сети, а не угадыванию.

Максимум ответа append ограничивается меньшим из прежнего максимума и остатка окна после полного входа и общего запаса. Он не задаёт минимальную длину или содержание ответа; прежние проверки неполного ответа сохраняются. Если окно не вмещает даже этот запрос, остаётся обычное сжатие. Ограничение должно доходить до поля `max_output_tokens` поддерживающего его маршрута; объявлять поддержку одной настройкой нельзя.

Для пилота обе стороны используют один маршрут Responses с наблюдением фактического расхода. Дополнительная запись `append-pilot-attempt` хранит фазу, безопасные поля отправленного тела и usage ответа; она не попадает в модельный контекст. Принятая сводка учитывает расход отвергнутых ответов append, а времена append и последующего обычного сжатия хранятся отдельно.

## Не входит

Внедрение, перезапуск без рабочего запроса, изменение рабочей policy окна, новая политика повторов, доказательство общей надёжности и отдельная система хранения состояния задачи.

## Проверка

Тесты сравнивают обычный и экспериментальный путь на одном событии сжатия: неизменность исходного префикса, окончательные обработчики запроса, бюджет полного входа, отмена и отклонение инструментов. Сквозной сценарий независимо проверяет результат задачи после сохранения сводки.

## Статус

Принято. Способ остаётся изолированным: маршрут включается только переключателем окна и не меняет рабочие настройки Pi.
